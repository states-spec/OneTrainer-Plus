# CLAUDE.md — OneTrainer

## Overview
- OneTrainer: diffusion-model trainer (full fine-tune, LoRA/LoHa/LoKr/OFTv2, embeddings) for SD1.5 through Flux/Chroma/Qwen/etc. Has a Qt GUI and a headless CLI.
- This repository is **OneTrainer+** (`states-spec/OneTrainer-Plus`), a fork of Nerogar/OneTrainer. The UI shows the name from `modules/util/app_info.APP_NAME` (window titles, top bar, settings/tooltip texts). The OneTrainer name stays wherever it is data or upstream's: file formats and keys (`onetrainer_config/`, LoRA layouts, metadata), `OT_` variables, the debug report file name, the wiki link, the launch scripts' `[OneTrainer]` prefix and the cloud pod name. The README credits upstream's authors and the Koratahiu ports; keep its Credits list current when porting more.
- Cloud training installs OneTrainer+ (user decision): `CloudConfig` defaults `install_cmd` to `git clone <app_info.REPOSITORY_URL>` and `onetrainer_dir` to `/workspace/OneTrainer-Plus` (the folder git clone creates: `LinuxCloud._install_onetrainer` runs the command in the parent of `onetrainer_dir` and now stops with a clear error when the folder isn't there afterwards). `CloudConfig.from_dict` replaces upstream's exact default pair (`git clone https://github.com/Nerogar/OneTrainer`, `/workspace/OneTrainer`, which the user's saved configs hold) with these, without a config version bump (the version stays aligned with upstream's), and prints a note once per process when the cloud is enabled (the UI and `scripts/train.py` both read a config twice); any other pair was set by hand and stays, and the exact upstream pair is replaced on every load, also when typed in. A new folder name means a cloud machine that has upstream in `/workspace/OneTrainer` gets a fresh clone instead of `update.sh` pulling upstream there. The repository is public, so the clone needs no credentials (a private repository would need them on the cloud machine).
- Built on diffusers + a custom graph data loader, **mgds** (pinned git commit in `requirements-global.txt`).
- User docs: [README.md](README.md), [LAUNCH-SCRIPTS.md](LAUNCH-SCRIPTS.md), [docs/](docs/). Don't repeat them here.

## Commands
Run from the repo root. Launchers `cd` there themselves, but raw `python scripts/...` must be started from the root: `factory.import_dir("modules/...")`, `resources/`, `secrets.json` and the default workspace paths are all relative to CWD.
```sh
./install.sh                     # create venv (default) or conda env, install requirements-global + platform file
OT_PLATFORM_REQUIREMENTS=requirements-rocm.txt ./install.sh   # skip GPU auto-detect (it picks /dev/nvidia0 before /dev/kfd)
./update.sh                      # git pull + pip install --upgrade --upgrade-strategy eager (re-pins torch!)
./start-ui.sh                    # PySide6 UI -> scripts/train_ui_qt.py
./run-cmd.sh train_ui_ctk        # legacy customtkinter UI (still maintained, same Base* views)
./run-cmd.sh train --config-path cfg.json                         # headless training
./run-cmd.sh train --preset-path "training_presets/Chroma/#chroma LoRA 24GB.json" \
    --config-path cfg.json --config-value epochs=1 --config-value transformer.train=true
./run-cmd.sh create_train_files --config-output-destination c.json \
    --concepts-output-destination concepts.json --samples-output-destination samples.json
./run-cmd.sh <script> -h         # any file in scripts/ (sample, convert_model, generate_masks, ...)
./run-cmd.sh generate_debug_report   # includes a "PyTorch GPU Runtime" section (HIP/CUDA build, gfx arch, VRAM, bnb library, /opt/rocm version)
./run-cmd.sh rocm_check [--full]    # GPU check suite (docs/GpuCheck.md): kernel correctness, training code, speed per model family
OT_DIAG_LOG=true ./start-ui.sh      # JSONL record of a run: memory, fragmentation, timing, loss (docs/RunDiagnostics.md)
./run-cmd.sh diag_report a.jsonl b.jsonl   # summarize/compare those logs
./run-cmd.sh diag_ab --config-path cfg.json --config-value epochs=1   # same config under variants (default: MemPool A/B)
./run-cmd.sh diag_ab --config-path cfg.json --variant 'a python:~/OT_A/venv/bin/python' --variant 'b python:~/OT_B/venv/bin/python'   # same code, two venvs (PyTorch/ROCm builds)
./run-cmd.sh rocm_check_compare a.json b.json   # rocm_check reports side by side: statuses, speed relative to the first
./run-cmd.sh train_probe --config-path cfg.json --steps 40   # per-step optimizer view: grads/moves per LoRA part, Prodigy D terms, outside changes, gradient check, mask/latent stats; saves nothing
./run-cmd.sh config_diff old.json new.json   # every setting that differs after loading both as training does (migrated), hidden UI settings included
ruff check .                     # lint config in pyproject.toml; E501 ignored, line-length 120
pre-commit run --all-files       # pre-commit hooks + ruff --fix (linter only, NOT ruff format)
```
- **No test suite.** No GitHub Actions workflows; only pre-commit.ci. Validate changes with `ruff check` plus a short real run (e.g. `--config-value epochs=1`).
- `scripts/rocm_check.py` (logic in `modules/util/rocm_check/`) is the only GPU-side check: the user runs it on the 7900 XTX and hands back `diagnostics/rocm_check/rocm_check_report.txt`/`.json`. Model shapes live in `shapes.py` (one row per family, not per model), so a new model type with new head/hidden sizes adds a row there. On the CPU, GPU-only checks skip; everything else runs (offloading uses `cpu:1` as the temp device).
- rocm_check section 5 trains a tiny random Chroma (`rocm_check/tiny_chroma.py`, built offline: SentencePiece T5 tokenizer, T5, Flux-layout VAE, transformer, masked captioned images) through the real `scripts/train.py` with the main workload's settings, seeded, once per variant (repeat = noise floor, MemPools, streaming off, offloading, resume; `--full` adds cache in RAM off, simplex, sync offloading, deterministic), and compares saved LoRAs and losses with the baseline; plus the model's components (T5, VAE, transformer + LoRA) GPU vs CPU. On the CPU every variant (offloading via `cpu:1`) and the resumed run are bit-identical to the baseline. `--full` adds "training features" (`workload_checks.training_features`, ~35 runs, ~10 min on the CPU): other optimizers, every LoRA format and adapter type, embeddings, fine-tune, validation, prior prediction/preservation (an image without a mask), losses, noise options, accumulation + fused back pass, saves with EMA, float8; each saved LoRA is loaded back at learning rate 0 and must save the same tensors (`_feature_variants` is the list to extend). `--full` also trains "compiled training" (`workload_checks.compiled_training`): Compile transformer blocks against the same run eager in a fresh compile cache (LoRA plus a warm-cache repeat, offloading, no checkpointing, DoRA, LoKr, OFT with CANS, float8, int W8A8 on the GPU; `_compiled_variants`), compared by the first step's loss and the weights' distance, not bit by bit. Section 3's "every optimizer" check builds all optimizers with the UI defaults (bitsandbytes ones only on the GPU), steps, resumes (bit-exact for all on the CPU) and runs the fused back pass where supported; its save helper names Muon's groups `<name>_<optim_type>` as `init_model_parameters` does (with plain names every Muon resume started fresh in the check, not in training).
- A training run that dies on a signal (a GPU fault, a device-side assert: ROCm aborts) ends its output with faulthandler's report, whose last line is the list of extension modules. `framework.output_tail` gives the report line the runtime's messages instead (a kernel's failed assert, which HIP prints through the device printf on stdout, HSA/HIP errors, an uncaught C++ exception) and each thread's innermost OneTrainer frame, the crashing thread first; the whole output stays in the run folder's `diag.log` (`run_child` reads both streams too).
- Triton builds a C helper (`hip_utils.c`) with the system compiler the first time it runs in an environment, and gcc's warnings go to the terminal mid-check: on the user's Fedora (GCC 16, a venv on Anaconda's Python 3.13) `'_POSIX_C_SOURCE' redefined` between `pyconfig.h` and glibc's `features.h`. Harmless and cached in `~/.triton/cache`; docs/GpuCheck.md says so.
- UI checks without a display: build `PySide6TrainView` with `QT_QPA_PLATFORM=offscreen` (needs `libEGL.so.1`, `libxkbcommon`, `libfontconfig`) and use `widget.grab().save(...)`. Before `findChildren`, flush `deleteLater()`d widgets with `QCoreApplication.sendPostedEvents(None, QEvent.Type.DeferredDelete)`, because `processEvents()` leaves them in place. The CTk UI needs a Python with tkinter plus Xvfb.
- `--config-value KEY=VALUE`: dotted keys walk nested `BaseConfig`s (`optimizer.beta1=0.9`); `None`/`null` clears a nullable field. `ema` is an `EMAMode` enum; the decay field is `ema_decay`.
- `--preset-path` turns off migration for **both** files, so the config must already be in the current format (`__version` 12).
- Python: min 3.11.1 (Pillow 13.0.0, pinned for its security fixes, needs 3.11; `version_check.py` also rejects 3.11.0, which Scalene doesn't support, so the minimum says so, as upstream's #1758 does; the launchers, `pyproject.toml` and `install.bat` check it), <3.14; conda path uses 3.13 (`lib.include.sh:35-38`). `OT_PREFER_VENV` defaults to `true` (Venv even if Conda is installed); set it to `false` to use Conda.

## Architecture (one training run)
```
scripts/train.py:main                      (CLI)          scripts/train_ui_qt.py -> modules/ui/PySide6TrainUIView.py (UI)
  TrainConfig.default_values()                             TrainUIController.start_training:318 writes training_presets/#.json
  .from_dict(preset, migrate=False)                          + secrets.json, trains in a thread on the *live* config object
  .from_dict(config, migrate=preset is None)
  --config-value overrides; secrets.json -> config.secrets
  -> modules/util/create.py:create_trainer:1592  (cloud.enabled -> CloudTrainer | multi_gpu -> MultiTrainer | GenericTrainer)

modules/trainer/GenericTrainer.py
  start():91
    create_model_loader  -> factory.get(BaseModelLoader, model_type, training_method)
                            e.g. modelLoader/ChromaLoRAModelLoader.py (make_lora_model_loader) -> modelLoader/chroma/*
    model_setup.setup_optimizations  -> per-part quantize / checkpointing / offload, attention backend (BaseModelSetup._setup_model_part)
    model_setup.setup_train_device
    model_setup.setup_model          -> LoRAModuleWrapper(...) per part, load lora_state_dict, hook_to_module()
                                        -> optimizer_util.init_model_parameters -> create.create_optimizer:300 + create_ema:1305
    create_data_loader   -> dataLoader/<Model>BaseDataLoader.py (registered per ModelType only)
                            DataLoaderText2ImageMixin._create_dataset:417 -> DataLoaderMgdsMixin._create_mgds -> mgds.MGDS/TrainDataLoader
    create_model_saver / create_model_sampler
  train():694   per epoch: dataset.start_next_epoch() (does caching) -> lr scheduler created lazily (create_lr_scheduler:1331)
                per batch: setup.predict -> setup.calculate_loss -> backward -> (update step) clip_grad_norm,
                           optimizer.step (or fused back pass hooks) -> lr_scheduler.step -> after_optimizer_step -> ema.step
                sample/backup/save go through TrainCommands; NaN loss raises RuntimeError
  end():951     backup (if backup_before_save) -> copy EMA into params -> model_saver.save(<final_output_dir>/<run_name><ext>)
```
- mgds stage order (`_create_dataset`): enumerate → load → mask aug → aspect bucketing → crop → augment → inpainting → **preparation** (model: VAE encode, tokenize, TE encode) → **cache** (`DiskCache` under `cache_dir/image`, `cache_dir/text`) → output (aspect batch sorting). The model-specific parts are `_preparation_modules`, `_cache_modules` and `_output_modules` in each `<Model>BaseDataLoader`. mgds source: `python -c "import mgds; print(mgds.__file__)"`.
- Per-model components (unet/transformer/text_encoder_N/vae…): `ModelType._MODEL_PARTS` (`modules/util/enum/ModelType.py:300`) is the single source of truth.
- Loss: `modelSetup/mixin/ModelSetupDiffusionLossMixin.py` (masked vs unmasked, flow-matching weighting); masked math is in `modules/util/loss/masked_loss.py`.
- Adapters: `modules/module/LoRAModule.py` (`LoRAModule`, `DoRAModule`, `LoHaModule`, `LoKrModule`, `OFTModule`, `LoRAModuleWrapper:898`). Export key conversion is in `modules/util/convert_lora_util.py`, and per-model savers are in `modelSaver/<model>/<Model>LoRASaver.py`.

## Extension checklists
### Registration mechanics (read first)
- `modules/util/factory.py`: `@factory.register(Base, ModelType.X[, TrainingMethod.Y])`, or a `make_*_model_{loader,saver}()` helper that registers internally.
- `create.py:53-57` auto-imports **only top-level files** in `modelSampler/ modelLoader/ modelSaver/ modelSetup/ dataLoader/`. The repo has no `__init__.py` files, so subfolders such as `modelLoader/chroma/` are never scanned. Registration must live in a top-level file.
- `modelLoader/stableDiffusion/StableDiffusionModelLoader.py` and `modelLoader/stableDiffusionXL/StableDiffusionXLModelLoader.py` import `create` inside the functions that use it: `create` imports every loader, so a top-level import made them fail when imported on their own (circular import).
- `factory.get` returns `None` when nothing is registered. The failure then shows up later as a `NoneType` error. DataLoader and Sampler lookups fall back to `(model_type)` without a training method.

### New optimizer
1. `modules/util/enum/Optimizer.py`: add the member. Update `is_adaptive`, `is_schedule_free`, `supports_fused_back_pass()` and `is_adv_optm` (adv_optm classes: resume version gate) if they apply.
2. `modules/util/create.py:create_optimizer`: add a `case`. The `match` has **no default**, so an unhandled enum gives `optimizer=None`.
3. `modules/util/optimizer_util.py:OPTIMIZER_DEFAULT_PARAMETERS[Optimizer.X]` is **required**; `change_optimizer` raises KeyError when the optimizer is picked in the UI. Its keys decide which params the UI shows. Their order is the settings window's layout (left, right, left, ... in `BaseOptimizerParamsWindowView`): a dropdown in a column of only checkboxes gets squeezed, so keep dropdowns where entries make the column wide. Leave out keys the optimizer ignores or that break it (ADAGRAD/RMSPROP/LARS/SGD_8BIT have no bnb settings `create.py` never passes). A setting that only works together with another one gets a rule in `OPTION_DEPENDENCIES` (`BaseOptimizerParamsWindowView`, also used by the Muon aux-Adam window), which greys it and its label out while the rule is false; a key the window doesn't show counts as unset.
4. A new hyperparameter needs: a `TrainOptimizerConfig` annotation plus a `default_values()` entry (`TrainConfig.py:83`/`:203`), a `KEY_DETAIL_MAP` entry in `modules/ui/BaseOptimizerParamsWindowView.py:94` (keys missing there are silently **hidden**), and use in `create.py`.
5. Pin the package in `requirements-global.txt`, or in the platform files if it has GPU builds. If it is CUDA-only, say so. bitsandbytes is pinned per platform file, currently 0.49.2 everywhere (the first 0.49.x with a `rocm72` binary; its CUDA wheels ship cuda126 and cuda130 on Linux, cuda118–130 on Windows). 0.50 removed the `percentile_clipping`/`block_wise` constructor args (percentile clipping is gone, 8-bit states are always block-wise); passing them raised a TypeError in ADAM(W)_8BIT, ADAGRAD_8BIT, RMSPROP_8BIT, LARS_8BIT, LAMB(_8BIT) and LION_8BIT, after the model had loaded (upstream's preview-2 pins 0.50.2 that way, #1756). Every bnb optimizer is built through `create._bnb_optimizer`, which passes them only where the installed bnb takes them and names a non-default value it can't apply. Checked by building all 14 bnb optimizers through `create_optimizer` (CPU, construction only): on 0.49.2 their settings are unchanged, on 0.50.2 all build (eight raised before). An actual upgrade still needs a GPU run, and a resume check of 8-bit states saved with Block Wise off (LAMB/LARS default).

### New config field (TrainConfig or a sub-config)
1. Add a class annotation **and** a `data.append((name, default, type, nullable))` in `default_values()`. Only fields in `default_values()` get (de)serialized; an annotation alone does nothing.
2. Supported types: `str/int/float/bool`, `Enum`, a nested `BaseConfig`, and `list`/`dict` of those (`BaseConfig.to_dict/from_dict`).
3. Renaming, moving or changing meaning: bump `config_version` (currently 13, `TrainConfig.py:679`) and add `__migration_N`. The fork's numbering is one ahead of upstream's until 13: the fork's `__migration_11` is its adv_optm renames and `__migration_12` is upstream's `__migration_11` (run names); upstream's `__migration_12` (13 there) only defaulted `oft_clipped_norm`, which needs no migration, so version 13 means the same in both and upstream's next migration is the fork's next too. **Also edit the built-in `training_presets/**/#*.json` by hand**, because they load with `migrate=False`.
4. UI: add a widget in the matching `modules/ui/Base*View.py` (shared by Qt and CTk) bound by name: `self.components.entry(frame, row, col, ui_state, "field")` or `"transformer.field"`. Choices come from the matching `*Controller`. A new widget kind has to be added to **both** `modules/util/ui/pyside6_components.py` and `ctk_components.py` (same function names).
5. Consume it in `modelSetup`/`create.py`/`dataLoader`. If it changes cached data, add it to the data loader's cache split names.
6. Optimizer fields: see "New optimizer" step 4. Per-part fields go on `TrainModelPartConfig`; the migrations fan per-part values out over all 12 part names.

## Conventions
- Naming: `<Model><Method>{ModelLoader,ModelSaver,Setup}.py`, `Base<Model>Setup.py`, `<Model>BaseDataLoader.py`, `<Model>Sampler.py`. Model-specific helpers go in lowercase subfolders (`modelLoader/chroma/`).
- Config: every config is a `BaseConfig` built from `default_values()`. Enums serialize as their string value (each enum defines `__str__`). `None` means "use the fallback in the consumer" for many optimizer fields.
- Setup classes are built from mixins (`modelSetup/mixin/`, `dataLoader/mixin/`, `modelLoader/mixin/`). Override the hook; don't copy the pipeline.
- UI = `Base*View` (toolkit-agnostic, gets a `components` module) + `Ctk*View`/`PySide6*View` (layout only) + `*Controller` (logic). `UIState` (`modules/util/ui/UIState.py`) writes widget changes straight into the config object. `""`/`"None"` become `None` only for nullable fields. `UIState.update(config)` copies the values into the vars and keeps `ui_state.obj` the object the traces write to (it used to rebind `obj` to the loaded copy, so views that read `ui_state.obj` after a preset load saw stale values). Widgets that only matter while another setting is on are greyed with `BaseTrainingTabView._enable_while` (built on `components.bind_var_trace`, in both component modules: a var trace removed with its widget); settings a model type or training method can't use are left out when the tab is built, and `change_training_method` rebuilds the training tab. Dropdown tooltips that explain each choice live in `modules/ui/dropdown_hints.py` (shown with `wide_tooltip=True`).
- UI preferences (settings tab: theme, UI scale, Qt font size, window size, Linux system file dialogs) are a separate `UISettingsConfig` in `training_user_settings/ui_settings.json` (gitignored), not part of `TrainConfig`. With no file, both UIs start **dark**, and System is dark unless the OS asks for light: Qt reports no preference (`Unknown`) for GNOME's "Default" style and without a portal, and the CTk UI reads GNOME's `color-scheme` (darkdetect says Light for `default` too); before, both fell back to light. The standalone CTk caption tool (`scripts/caption_ui.py`) applies the saved theme and scale too (it ran on customtkinter's own System mode). At startup the portal's answer arrives after the theme is applied (Qt reads it asynchronously), so System on a light desktop starts dark and switches within the first event-loop turns (tested with a fake `org.freedesktop.portal.Settings` service on the session bus). The Qt top bar's ◐ button toggles light/dark through the same `theme` setting, and `last_tab` reopens the last tab. Qt applies the scale only at startup (`create_application` sets `QT_SCALE_FACTOR` unless it is already in the environment). CTk applies the theme only at startup, because labels in its transparent scrollable tabs keep their old background after a live switch.
- Qt: a widget polished by the application style sheet keeps the palette and font it had then (`QApplication.setPalette`/`setFont` alone left ~750-960 of 1270 widgets unchanged), so theme and font changes polish every widget again in `pyside6_util._restyle_widgets`: once each, parents first, the StyleChange events children first. Don't re-set the application style sheet for that: Qt's `QStyleSheetStyle::repolish` polishes each widget once per ancestor, 0.5 s per change with 1270 widgets and 1.5-1.8 s with 3000 (the user saw 2-5 s); `_restyle_widgets` takes 0.1 / 0.25-0.34 s and gave pixel-identical screenshots (13 tabs x 9 theme/font states, offscreen and on Wayland) and the same font, palette and size on every widget, hidden tabs and open dialogs included. So `_STYLESHEET` is set once at startup and holds nothing theme- or font-dependent; a progress bar's trough color is in its own style sheet (`style_progress_bar`, called where each `QProgressBar` is created). The checkbox indicator rule (`_checkbox_indicator_style_sheet(16)`, added at startup) is in em, which Qt style sheets take as the line height of the application font and recompute at every polish, scaled so the default font size still gives 16 px: it grows and shrinks with the Font Size setting (it stayed 16 px from 8 to 18 pt). The concept cards' checkbox stays a fixed 20 px: the card, its image and buttons are fixed-size. `_on_color_scheme_changed` re-applies the System theme only when the darkness changed (it used to apply twice per switch to System). Programmatic `var.set()` on a `QtVar` runs widget callbacks (e.g. a dropdown's `command`) **before** the trace that writes the config, so write the config first when a callback reads it (`LoraTabController.activate`). `add_var_trace`/`remove_var_trace` with a dotted name (`"quantization.layer_filter_preset"`) register on the nested state that owns the var; they used to register on the root state, where the trace never ran (the quantization layer filter kept the visibility of the preset shown when the model tab was built). The layer-filter widgets rewrite `layer_filter` from the preset's patterns whenever the preset var changes, so a built-in preset's `layer_filter` must equal its model's `LAYER_PRESETS` entry, or loading it changes the value (Hunyuan Video's said `transformer_blocks`).
- Every `QTabWidget` calls `pyside6_util.style_tab_widget` (main window, concept window, video tool): its page area takes `_TAB_PAGE_ROLE` (`AlternateBase`: Fusion never reads it, and no view here alternates its row colors), which the pages and the scroll areas in them inherit, also those a rebuild creates: the window color in the dark theme (#2d2d2d), Fusion's tab frame color in the light one (`_tab_frame_color`, #fbfbfb). Before, pages without a scroll area (LoRA, settings) showed the tab frame (#434343 in dark) and the others their scroll area's window color (#efefef in light). Don't give a widget in a page its own background role or fill. Transparent scroll content would have matched them too, but doubled the repaint per scroll step (training tab 6 -> 13 ms).
- A `QDialog` with a parent stays alive after `exec()` returns until it is deleted. The optimizer, scheduler, timestep and convert windows delete themselves on `finished`; the concept window once its stats scans have stopped (`_delete_when_scans_stopped`: they report to its widgets through `call_after`, which doesn't check for deleted widgets), and it runs `_cleanup` on `finished` too (Escape/`reject()` sends no closeEvent, so it left the scan running). Each opening used to leave its widgets behind (concept window ~250, convert tool 55), all restyled at every theme or font change. The video tool still stays (113 widgets per opening): its jobs run in untracked threads that report to it until they finish. Plots use a `matplotlib.figure.Figure` of their own, not `plt.subplots`: pyplot's Qt backend keeps a hidden 15-widget window per figure, even after `plt.close`. Their colors come from the palette (`tab_page_color` for a plot on a tab page); the timestep preview was matplotlib's white in the dark theme.
- Qt widgets (and `QPixmap`) may only be touched on the UI thread. Worker threads (concept stats scan, sampling, video tool, training callbacks) hand UI work over with `components.call_after(widget, 0, fn)` or `schedule_on_main_thread` (`QTimer.singleShot(0, context, fn)` runs `fn` in the context's thread). A direct call from a thread may freeze or crash the app on a real desktop, even when offscreen tests pass.

## Gotchas
**Config loading**
- `BaseConfig.from_dict` (`:66`) **never fails**. A missing key keeps its default. A bad value prints `Could not set X as Y` (`:136`) and is skipped. Unknown keys (e.g. `weight_dtype` in the Chroma presets) are ignored silently.
- Loading a preset in the UI applies it over **defaults**, not over the current config (`TopBarController.load_config_from_file`). A filename starting with `#` (except `#.json`) is treated as built-in and **skips migration**. Like `scripts/train.py`, the load goes on top of `default_optimizer_config(optimizer)`, and the loaded optimizer settings become that optimizer's `optimizer_defaults` entry (they used to be overwritten by it).
- `optimizer_defaults` remembers each optimizer's settings for switching back to it; the optimizer window saves into it through `OptimizerParamsWindowController.on_close`, which every widget command calls. It skips saving while it loads an optimizer's settings into the window (a save then stored a half-updated mix).
- The concepts/samples tabs pick their file through a dropdown of `training_concepts/`/`training_samples/`. The file a config names is always added to it (`BaseConfigListView.__list_config_file`), and `reload_from_config()` runs after every config load: before, a file outside those folders left the previous list shown, and saving wrote it over the loaded config's file.
- Switching the model type sets `base_model_name` and the other parts' `model_name` (decoder, effnet, HiDream's Llama) from the built-in presets, or from `TopBarController.FALLBACK_BASE_MODELS` for types without a preset, but only while the field is empty or holds another type's default.
- Input validation (`util/ui/validation.py`): floats must be non-negative except `SIGNED_FLOAT_FIELDS` (noising bias/weight, Adafactor's `decay_rate`), and an empty non-nullable int/float is "Value required" (it used to be stored as `None`).
- The UI restores the last session from `training_presets/#.json` (gitignored, like every user-saved preset: the root `.gitignore` ignores `/training_presets/**/*.json` except `#*.json`, so a new built-in preset must be named `#*.json` or git skips it). Without it (fresh clone or worktree) the UI starts as SD1.5 / Fine Tune, which has no `blocks` layer-filter preset (only transformer models define one). The LoRA, embedding and additional embeddings tabs are always shown. LoRA/embedding are greyed out with a "Switch to ..." button unless their method is selected, or show a "not supported" note for models without it (`util/ui/training_method_notice.py`); additional embeddings are greyed out with a note on models without embedding training (`BaseAdditionalEmbeddingsTabView.update_supported`, re-applied after every list change). If `#.json` fails to load, it is copied to `#.json.bak` first, because closing the UI overwrites `#.json` with the defaults. On a fresh install the concepts/samples tabs write their empty default list (`training_concepts/concepts.json`, `training_samples/samples.json`) before loading it (`BaseConfigListView.__load_available_config_names`); loading it first printed "Failed to load config from ...: No such file or directory" at the first start. That branch only adds the entry: the dropdown is built in `build()` after the file the config names is listed. Building it in the branch (upstream's code) switched a restored `#.json` whose lists live outside those folders to the empty default at the first start of a fresh clone, because both toolkits' `options_kv` select the first entry when the value isn't listed (the files stayed intact, the config just pointed elsewhere).
- Every optimizer gets the UI's `OPTIMIZER_DEFAULT_PARAMETERS` on the CLI too: `scripts/train.py` loads the config on top of `default_optimizer_config()`, and `create_optimizer` fills unset (None) settings from the table, except where None is itself a setting (`optimizer_util._NONE_IS_A_SETTING`, e.g. prodigy-plus `eps=None` = Adam-atan2). Explicit non-null values always win, so a `create_train_files` template switched to another optimizer keeps its written bools (e.g. ADOPT_ADV `use_atan2: false`, UI default true).
- The final model goes to `final_output_dir`/`run_name` + the format's extension (`TrainConfig.get_output_model_destination`); `output_model_destination` and `save_filename_prefix` are gone (preview-2 #1744; `__migration_12` turns them into `run_name`/`final_output_dir`, `run_name_mode` CUSTOM). `run_name_mode` DEFAULT (`<method>_<timestamp>`) and FRIENDLY (two `friendlywords`) pick a new name for every run; CUSTOM keeps `run_name`. `BaseTrainer` keeps the name it is given (CloudTrainer and the remote run must agree on it), so the entry points renew it: `scripts/train.py` always for those two modes, the Qt UI at startup and after each run, and `TrainUIController.start_training` when the name was already used (its `workspace/config/<name>.json` or final model exists, e.g. a loaded config). Before, a config saved from the UI kept its run's name, and every CLI or CTk run of it wrote over the same final model. A new config defaults to DEFAULT, so it no longer overwrites the same file each run. The built-in presets still carry an ignored `output_model_destination` key, as upstream's do.
- `output_model_format` defaults to `SAFETENSORS`, which saves only embeddings. The UI's Output Format dropdown switches to the first valid format, but a CLI config (e.g. the `create_train_files` template) has to set one from `ModelType.supported_output_formats(training_method)`. `GenericTrainer.start` raises otherwise; before that check, the saver failed at the first save, after the training.
- LARS, LARS_8BIT, SGD_8BIT and SCHEDULE_FREE_SGD reject `momentum: 0`, and DADAPT_ADA_GRAD rejects `eps: 0.0` (defaults are now 0.9 / 1e-6). Configs saved with the old values still fail until the value is changed.
- Before loading, `_validate_hf_repo_access` (preview-2 #1683) checks Hugging Face repos for gated/missing access and names the repo from the request URL. Without network (`httpx.TransportError`) it skips the check, so a cached model still loads offline.
- A config file without `"__version"` is migrated from version 0, and `__migration_0` crashes (`unhashable type: 'dict'`) if `optimizer` is a nested object. Always keep `__version`.
- Saved configs (`to_settings_dict`) point to `concept_file_name`/`sample_definition_file_name` by path. Exported "pack" configs (`to_pack_dict`) inline them. `samples.json` is re-read at every sample.
- `layer_filter_preset` exists only for the UI. Training reads only `layer_filter` (comma-separated substrings, or regex when `layer_filter_regex`). In LoRA setups it applies to the denoiser wrapper only, not the TE LoRA. A filter that matches nothing raises `ValueError`.

**Optimizers / schedulers**
- `is_schedule_free` optimizers (SCHEDULE_FREE_ADAMW/SGD, PRODIGY_PLUS_SCHEDULE_FREE) are **silently forced** to a CONSTANT scheduler with no warmup (`create.py:1357`, `:1442`). PRODIGY_ADV is *not* flagged schedule-free.
- `learning_rate_warmup_steps` (default **200**): >1 means steps (divided by grad-accum), 0<x≤1 means a *fraction* of total steps (so `1` means warmup across the whole run), ≤0 means none (`create.py:1348`).
- The ADV optimizers get `k_warmup_steps = learning_rate_warmup_steps / grad_accum` for Kourkoutas-β (`create.py:861,881,909`). With LR warmup at 0, that warmup is 0 too.
- `ADAM_8BIT`/`ADAMW_8BIT` use `bnb.optim.Adam8bit`/`AdamW8bit` (always 8-bit state; tensors < `min_8bit_size` stay fp32; `amsgrad` unsupported). bnb picks the update kernel from the stored state dtype, so old 32-bit state from a backup keeps working. ADAGRAD, RMSPROP, LARS (`optim_bits`/`min_8bit_size`/`percentile_clipping`/`block_wise`), ADAGRAD_8BIT (`optim_bits`) and SGD_8BIT (`min_8bit_size`/`percentile_clipping`/`block_wise`) used to show settings `create.py` never passes; the UI no longer shows them, and values in old configs are ignored as before.
- bitsandbytes backs every `*_8BIT` optimizer plus ADAGRAD, RMSPROP, LARS, LAMB and AdEMAMix (even 32-bit), and the `INT_8`/`NFLOAT_4` weight dtypes. `*_COMPRESSED` dtypes need nvCOMP (NVIDIA only; its CUDA build has no AMD code and needs NVIDIA's driver, so they can't work on ROCm, verified on the pinned 5.3.0.16 wheel) and `GenericTrainer.start` stops on them before loading when it is missing, naming the uncompressed dtype to use (the loader's own stop in `quantization_util` stays). They stay in the model tab's dropdown on ROCm for now; on a ROCm or CPU-only PyTorch build `nvcomp_util` doesn't try the backends, so its "no backend available" line no longer prints at every start. `INT_8` (bnb `Linear8bitLt`) can't be built since upstream #1034, in the fork and upstream alike (FIXME in `quantization_util`).
- bnb's LARS is SGD with momentum whose update is capped at `max_unorm` × the weight norm, on momentum's kernels. 0.49.2 has no "lars" in its 32-bit kernel table (the 8-bit one still maps it to momentum's, as older releases did for both), so every LARS step and LARS_8BIT's tensors under `min_8bit_size` raised `Unsupported optimizer name: lars` (the GPU check found it). `create._bnb_lars_on_momentum_kernels` sets the name to "momentum" (not saved in the state). bnb's optimizers refuse CPU tensors; with that guard bypassed its pure-torch backend matched a reference LARS to 1.2e-7 and resumed bit-exactly (LARS_8BIT's 8-bit kernels exist only in the GPU library). On the 7900 XTX (0953151) both step and resume bit-exactly and move as that backend does on the same inputs (the every-optimizer loop: 9.8e-5 in 6 steps; 7.8e-2 without the cap, the GPU's SGD_8BIT figure).
- The A8 dtypes (`BFLOAT_16_A8_INT`/`_FLOAT`, preview-2 #1108) quantize only the activations: bf16 weights that full fine-tuning can train. The 8-bit matmuls are Triton kernels (`triton_mm_8bit`, with the fused scale+LoRA epilogue of #1680) that autotune over 14 configs sized for NVIDIA's ~99 KB shared memory; few fit gfx1100's 64 KiB LDS. Measured on the 7900 XTX (`rocm_check` at 42a68fe): every kernel correct (K padding, epilogue 5.9e-8), autotuning took ~1.5 min, int8 matmul 0.78x the speed of bf16, int W8A8 fwd+bwd 0.83x, bfloat16 A8 int 3.47 ms vs 1.06 ms for a *frozen* bf16 layer (the check now times a trainable one). A8 keeps the bf16 input for the backward, so it saves no memory; with int8 at the bf16 rate on RDNA3 it is only slower there.
- The float W8A8 dtypes (`FLOAT_W8A8`, its compressed variant, `GGUF_A8_FLOAT`, `BFLOAT_16_A8_FLOAT`) run `torch._scaled_mm`, which PyTorch allows only on fp8 hardware (NVIDIA sm89+, AMD gfx942/gfx950/gfx1200/gfx1201). `GenericTrainer.start` probes it (`torch_util.fp8_matmul_supported`) and stops before loading; it used to fail at the first forward, after caching. On gfx1100 (RDNA3), int8 goes to native WMMA (hipBLASLt ships navi31 I8II kernels for `_int_mm`; Triton emits `v_wmma_i32_16x16x16_iu8`) and fp8 only as an fp16 upcast, and RDNA3 runs int8 WMMA at the bf16 rate: W8A8 saves memory but is not faster there, same as `FLOAT_8` (W8, weight-only). The W8A8 backward is a Triton kernel, so W8A8 can't train on the CPU. Its first use autotunes 16 variants: for gfx1100 the int8 ones compile in ~3 min in total (5 of them need more than the 64 KiB LDS and are skipped at launch), but the fp8 ones (emulated via fp16) took >10 min each, which is why `rocm_check` tests fp8 only where `fp8_matmul_supported`.
- A layer-offloaded part in FINE_TUNE requires an optimizer with `supports_fused_back_pass()` **and** `fused_back_pass=true` (`create.py:316`).
- ADAM/ADAMW (UI default `fused: true`) take Fused Back Pass and Stochastic Rounding only with Fused and ForEach off: the optimizer window greys both out then (`OPTION_DEPENDENCIES`), and `check_optimizer_config` refuses the combination before the model loads (`create_optimizer` refused it after loading).
- Fused back pass: each parameter's grad hook binds its own group's step function (`optimizer_step=__optimizer_step` default arg). It used to close over the loop variable, so every parameter was stepped with the **last** group's lr/betas/eps/wd (SD1.5 fine-tune, text encoder lr 0: 36/36 TE tensors changed). Without clipping, fused and normal steps are bit-identical. With clipping they differ: a fused back pass clips each parameter's gradient on its own (the global norm only exists after the back pass); `__apply_fused_back_pass` prints a note.

**adv_optm (the `*_ADV` optimizers, pinned 2.6.3)**
- 2.6.0 (upstream preview-2 #1756) only adds settings: `scaled_wd` on every ADV optimizer and SinkSGD_adv's `oft_mode`; every other code path and the state layout are as in 2.5.16 (tagged LoRA/DoRA/OFT/embedding groups, 8 optimizers x 7 setting sets: bit-identical weights, SinkSGD's OFT group aside). `scaled_wd` ("Scaled Weight Decay", off): decay ÷ the matrix's input width (`numel / shape[0]`), OFT blocks × 2/(b-1), none on vectors (`_is_dora_scale`, 1D) for the normal decay, and `decay_factor = lr / _init_lr` (the constructor lr, `config.learning_rate`; Prodigy passes d·lr, so × D) instead of × lr; checked exactly on one zero-gradient AdamW_adv step. Without weight or centered decay it does nothing (`OPTION_DEPENDENCIES` greys it). It is passed only when on, so a venv still on 2.5 (a `git pull` without `update.sh`; launchers don't reinstall) trains unchanged, and `check_optimizer_config` stops before loading if it is on there. `oft_mode` normalizes OFT updates with a skew-symmetric Sinkhorn; it treats every matrix of its group as OFT blocks. Upstream sets it for the whole optimizer when `peft_type == OFT_2`, so fine-tuning or embedding training with OFT still selected, and additional embeddings next to an OFT LoRA, fail at the first step (index_put shape mismatch, reproduced on 2.6.0). `create._sinksgd_oft_mode_groups` sets it per group, only where every matrix is a tagged OFT block; rocm_check's training features cover SinkSGD on OFT with an additional embedding and ADOPT_ADV with scaled weight decay.
- 2.5 removed AdEMAMix / Simplified AdEMAMix (`use_AdEMAMix`, `beta3_ema`, `alpha_grad`, `Simplified_AdEMAMix`), Lion's `clip_threshold` and `Lion_Prodigy_adv`. Their successor is `nesterov` + `nesterov_coef` (update = coef·momentum + (1−coef)·grad; `None` = beta1/momentum; needs beta1/momentum > 0). The bitsandbytes `ADEMAMIX`/`ADEMAMIX_8BIT` optimizers are separate and unchanged, and so is the shared `alpha` field.
- `orthogonal_gradient` is a mode string (`disabled`/`flattened`/`iterative`), not a bool: adv_optm returns `None` for a bool mode, which nulls every gradient. `create._adv_orthograd_mode` maps a leftover bool (also in the Muon aux-Adam dict). `nnmf_factor` became `state_precision="factored"` except on LION_ADV, which has no `state_precision`. `__migration_11` does these renames.
- `state_precision` values that work are listed by `optimizer_util.adv_state_precisions` (UI dropdown and a `ValueError` in `create.py`): `fp16` breaks everything but ADOPT_ADV (and ADOPT_ADV with `factored_2nd`, refused up front; with Nesterov too before 2.6.2), `factored` broke ADAMUON_ADV up to 2.5.13 (offered again on 2.5.16), and SINKSGD_ADV `factored` with momentum 0 is passed as `auto` (no state to factor). Muon/AdaMuon without the aux Adam crash on 1D params (biases, norms) in both 2.2.3 and 2.5.13; LoRA params are 2D. `muon_util.split_parameters_for_muon` raises a clear error before the first step (it used to be an `UnboundLocalError` after caching). `snr_cond` (SignSGD/SinkSGD) only works with normed momentum and momentum > 0 and adv_optm raises without them; `create._effective_snr_cond` passes it off then.
- Resuming: optimizer.pt carries `adv_optm_version`. A minor version with another state layout (or none, i.e. ≤2.2) drops the optimizer state with a warning; 2.5 and 2.6 share one (`create._ADV_OPTM_COMPATIBLE_STATES`): 2.5.16 states resumed on 2.6.0 continue exactly as on 2.5.16 (64 optimizer/setting cases; the int8_sr ones differ from an uninterrupted run on either version, because adv_optm's stochastic-rounding generator restarts at seed 42 in a new process), and settings a 2.5 group lacks come from the config (`old_group.setdefault`); weights/EMA/progress still resume. A D-adapting optimizer (`is_adaptive`: Prodigy, D-Adaptation) on a fresh state restarts D at Initial D and measures it from the backup's already-trained weights, so D can stay there: the user's Chroma LoRA, resumed after a crash from a backup another optimizer had made, kept D at 1e-4 for 450 steps (tiny Chroma, fresh Prodigy on a trained LoRA: 4.7e-4 after 75 steps vs 1.4e-2 from scratch). So for a same-optimizer backup of another adv_optm version, `create_optimizer` keeps the saved group's `d`/`d_max`/`k` (one number each) and drops only the per-parameter statistics; a backup made with another optimizer (OneTrainer starts the group fresh, which used to be silent) now prints which groups start fresh, and for D optimizers an Initial D matching the backup's step size (its `lr` × `d`). `continue_last_backup` takes the newest *complete* backup in the workspace (`TrainConfig.get_last_backup_path` skips folders without `meta.json`, which every internal saver writes last: a crash while writing left a folder that resumed only the weights, with a fresh optimizer and progress 0) from whichever run made it, so after a crash before the run's first backup it resumes an older run's backup; it skips backups whose `onetrainer_config/args.json` has another `model_type`, `training_method` or (LoRA) `peft_type` (backups without it are still used), and the start message names the backup's run and step (`TrainConfig.describe_backup`). A same-run Prodigy backup resumes with D intact (tiny Chroma, early and mid-run). A stuck state resumes stuck too: once `d_numerator` (sum of dot(grad, start - weights)) is negative, D can't grow, and `continue_last_backup` carried such a state from run to run in the user's workspace, which looked like fresh runs stalling (train_probe: optimizer state present before step 1, d_numerator -1.2e-5 → -6.3e-5 over two 60-step runs, D 1e-4 throughout; a new workspace adapted D from step 27). `create_optimizer` warns on resume when a group's D still equals Initial D after ≥ 20 steps with a negative numerator, and `GenericTrainer.train` asks `create.d_at_initial_training_warning` once, 100 optimizer steps into a run: Prodigy only raises D, so D still at Initial D means the estimate never reached it (Initial D or the LoRA alpha too high: the user's alpha 32 / Initial D 1e-4 run; tiny Chroma with Initial D 0.5 keeps d_numerator positive but D at 0.5). train_probe prints `RESTORED optimizer state`. ADAMUON_ADV's Nesterov defaults to on (preview-2 and adv_optm 2.5.16's own default). On load, `create.py` also works around two adv_optm bugs (found on 2.5.13; the workarounds still run on 2.5.16): it sets `actual_state_precision` on groups that lack it (Lion, all-factored), and `_restore_adv_optm_state_dtypes` puts the saved state tensors back after `load_state_dict`, because torch's per-param cast plus adv_optm's re-cast broke `int8_sr` (signed → uint8), fp32 state on bf16 weights, and fp32 vector state in `factored` mode.
- Resuming keeps the **backup's** optimizer settings (betas, eps, weight decay, Nesterov, Kourkoutas-β, d_coef, ...); only `lr`/`initial_lr` come from the config (`create_optimizer`, upstream design, any optimizer). It now prints a warning listing every setting that differs (`_changed_optimizer_settings`: keys named like `TrainOptimizerConfig` fields, plus `betas`/`compiled_optimizer`; `k` is excluded, it is Prodigy's step counter). adv_optm builds the Kourkoutas-β helper only in the constructor but reads the flag from the restored group, so a Kourkoutas backup resumed with the option off failed in the first step; `_restore_kourkoutas_helper` builds it after loading.
- **PRODIGY_ADV's Nesterov was broken before adv_optm 2.6.1.** Prodigy_adv keeps `exp_avg` in D units (`exp_avg.mul_(beta1).add_(grad, alpha=d * (1 - beta1))`, like Prodigy), but up to 2.6.0 (and every pre-release: 2.6.dev1, 2.6.1.dev1–3, 2.6.2.dev2) its Nesterov step did `exp_avg.lerp_(grad, 1 - coef)` with the raw gradient, a term 1/d too large: each step moved every weight by ~(1 - coef)·lr whatever D was (the user's Chroma LoRA at lr 1: noise within the first steps; AdamW/Adopt/SignSGD/SinkSGD_adv keep momentum in gradient units and were unaffected). **Adapters**
- DoRA is `lora_decompose` for LoRA and `lokr_weight_decompose` for LoKr. LoHa and OFT v2 have no DoRA path; `lora_decompose` is ignored for them.
- Conv LoHa factors are saved in the LyCORIS 2D layout (`hada_w*_a` [out, rank], `hada_w*_b` [rank, in·k·k]); `LoHaModule._load_from_state_dict` also accepts the older 4D layout.
- LoKr uses `lokr_dim` (not `lora_rank`) and `lora_alpha`. If `lokr_dim >= max(w2 dims)/2`, it prints "using full matrix mode" and makes W2 full (`LoRAModule.py:365`). If W1 and W2 both end up full, **alpha is overwritten with `lokr_dim`** (scale 1, `:445`), so `lora_alpha` is ignored.
- `lokr_decompose_factor=-1` (the default) factorizes near √dim; for example 3072 → 48×64.
- LoKr's forward without DoRA runs the base layer and the delta weight as two matmuls; with DoRA it merges them into one. `lokr_vec_trick` (upstream default **true**, Linear layers only) applies the factors by einsum instead of building the delta. On the 7900 XTX (`rocm_check --full`, 2x1024 tokens, 3072x3072, fwd+bwd): vec trick 4.53 ms, dense delta 3.32 ms, LoKr + DoRA 2.68 ms, no adapter ~1.8 ms. The vec trick saves the dense delta weight (18 MiB per 3072x3072 layer in bf16, plus its gradient) but is the slowest path there.
- OFT's rotation is the 5-term Cayley-Neumann series (Horner form, 2 matmuls), which drifts from orthogonal as rotations grow (3e-3 at spectral norm 0.33, 36% at 1.1, diverges past ~3). `oft_cans` computes the exact Cayley transform (I+Q)(I-Q)^-1 via a CANS Newton-Schulz polar iteration (1e-7 in fp32, ~15 small matmuls: no measurable time on a 3072-wide layer, +4.9 MiB saved for backward per layer in fp32). It is off by default: PEFT, the reference for this `oft_R` layout, applies the same 5-term series by default (`use_cayley_neumann=True`), and ComfyUI core loads only LyCORIS `oft_blocks`, not this format. It saves no marker key (same file format). `use_cayley_neumann=False` (never set by OneTrainer) now takes the exact CANS path; it used to solve for (I-Q)(I+Q)^-1, the *inverse* rotation (copied from PEFT, whose exact mode has the same inconsistency). From the adv_optm author's fork; its matrix-exp OFT is not ported. DoRA-OFT (`dora_oft`, a `dora_log_multiplier` vector per layer) and spectral norm clipping came with upstream preview-2 (#1335, #1751). CANS's per-step coefficients come from the opaque custom op `ot_oft::cans_coefficients`: inlined, each step's bounds use the previous step's several times over and inductor built an exponentially growing expression (a block with CANS OFT layers didn't compile in 20 minutes; the `(B, 1, 1)` bmm meant to stop that is turned into an elementwise multiply by inductor's bmm decomposition since at least torch 2.12). The op runs the old operations under the caller's autocast (passed in) and returns each coefficient in the dtype it had (fp32 at step 0, bf16 later under bf16 autocast, which decides how `c3 * bmm(A, X)` rounds): eager training is bit-identical to before, compiled matches it to bf16 rounding. Under bf16 autocast all of the CANS rotation (the clipping's power iteration, (I+Q)^2, every step and the bounds) ran in bf16, which kept it ~5e-3 from orthogonal (about the 5-term series' error at small rotations); `oft_cans_fp32` (LoRA tab "CANS in Float32", greyed while CANS is off; default on, the user's decision 2026-11-06 after the GPU numbers below, so configs saved without the key train in float32 and off reproduces the old results) builds it with autocast off in float32: 1e-7, no measurable cost on the CPU (3072-wide layer), and without autocast with fp32 OFT weights it computes the same as off. rocm_check's adapters check prints both rotations' orthogonality and times both: on the 7900 XTX (af25169) 4.1e-3 vs 1.1e-7, 2.98 vs 2.93 ms fwd+bwd on a 3072-wide layer (plain OFT 1.78 ms), and against the fp32 CPU reference bf16 CANS was the least accurate adapter (4.3e-3) while CANS in Float32 matched plain OFT (3.5e-3).
- OFT spectral norm clipping (`oft_clipped_norm`, empty = off, the default): one power-iteration step per training forward estimates each block's spectral norm and scales Q down to the limit; it applies before the series and before CANS. The estimate (`u_state`/`v_state`) is not saved, so it restarts after a resume, and a checkpoint recompute advances it a second time; once it has converged, checkpointed and plain gradients match to 1e-6. The file gets an `oft_R.clipped_oft` marker per layer, as Scaled OFT gets `oft_R.scaled_oft`; inference has to apply the same clipping. `GenericTrainer.start` refuses a limit ≤ 0 (0 divided 0 by 0 on the zero-initialized first step). Upstream left `.clipped_oft` out of `DOUBLE_SEGMENT_SUFFIXES`, so every clipped file failed to load back. `oft_scaled` defaults to false: upstream's #1746 set it true, and #1751 set it back three days later without comment.
- The output format changes the adapter's structure. `ORIGINAL_LORA/COMFY_LORA/KOHYA_LORA` build **fused qkv** adapters (`ModelFormat.needs_qkv_fusion`), while DIFFUSERS/LEGACY keep them split. Resuming a LoRA or backup under a different fusion mode fails `check_fusion_match`.
- A LoRA file with layers outside the current layer filter keeps them as dummy modules (`LoRAModuleWrapper.load_state_dict`). Each dummy gets only its own layer's keys (key minus 2 segments for `.weight`/`.scaled_oft` suffixes, `DOUBLE_SEGMENT_SUFFIXES`, else 1); hook/unhook/dropout skip dummies. Before: a crash ("Should never be called on a dummy module"), OFT layers dropped, and dummies holding the whole dict overwrote the trained layers at save.
- A LoRA file's bundled embeddings (`bundle_emb.<placeholder>.<key>`, `bundle_additional_embeddings`, on by default) are read back when the file is `lora_model_name`, for embeddings without their own `model_name` (`EmbeddingLoaderMixin`, matched by placeholder, which `EmbeddingName` carries; they used to restart from their initial text). The bundle keys equal the embedding files' keys except SD 1.x/2.x (`clip_l` vs the A1111 `emp_params`, mapped by `StableDiffusionEmbeddingLoader._bundle_key_names`). Backups keep embeddings in `embeddings/<uuid>.safetensors`. Every LoRA format, LoHa, LoKr + DoRA, DoRA, OFT (DOFT, CANS, clipping) and a bundled embedding reload bit-exactly (tiny Chroma, lr 0 round trip). `HiDreamEmbeddingSaver` wrote the clip_g output vector as `t5_out` (overwritten by T5's); it is `clip_g_out` now.
- `ORIGINAL_LORA` holds one component only (no TE LoRA, no bundled embeddings), and `COMFY_LORA` needs a Comfy name for every trained text encoder. `GenericTrainer.start` calls `model_saver.check_can_save` (`LoRASaverMixin`) before loading; it used to fail at the final save, after the whole training.
- `DIFFUSERS_LORA` (the Chroma LoRA presets' format) with per-input DoRA (`*_dora_on_output`/`lora_decompose_output_axis` off) stores `dora_scale` that diffusers drops. LoHa/LoKr/OFT in DIFFUSERS format can't be loaded by HF diffusers (`convert_lora_util.py:162`).

**Data / masking**
- `unmasked_probability` works **only** for inpainting models (`has_mask_input()`); for Chroma and every other txt2img model it does nothing (`DataLoaderText2ImageMixin.py:312`). For those, masked training uses `unmasked_weight` + `normalize_masked_area_loss`. Tested on upstream master with tiny Chroma, Flux, SD1.5, SDXL and their inpainting counterparts (SD1.5/SDXL inpainting, Flux Fill), 3 optimizers and 3 dataset layouts: on the txt2img models 0 vs 1 and a black vs a noise `-condlabel` image gave bit-identical weights and identical batch masks; on the inpainting models both changed the weights (p=1 made every batch mask full). Upstream gated mask removal to `has_mask_input()` in the commit that added masked training (2023-04-12) and still does; custom conditioning images came with PR #812 for Flux Fill. Upstream gives inpainting models the **unmasked** loss even with masked training on (`TODO: don't disable masked loss functions when has_conditioning_image_input is true`); here every model gets the masked loss (`ModelSetupDiffusionLossMixin`), so `unmasked_weight`, `normalize_masked_area_loss` and masked prior preservation work on inpainting models too, and `unmasked_weight: 1` gives upstream's loss (bit-identical on tiny SD1.5/SDXL inpainting and Flux Fill). Flux Fill's `latent_mask` is the pixel mask packed 8x8 into 64 channels (`ShuffleFluxFillMaskChannels`, the model input), which is why upstream couldn't just drop the gate: `__loss_mask` weights the loss by the mean of those channels, each latent pixel's 8x8 block average. Upstream's docs never mention either option; the wiki's Training page describes unmasked probability as a general setting and unmasked weight as a weight "during unmasked training of the area where the mask is", both contrary to the code. `docs/QuickStartGuide.md` now spells out the per-model behavior.
- Upstream (2026-08) crashes with `KeyError: 'latent_mask'` when a cache made with masked training off is reused with it on (`clear_cache_before_training` off; discussion #700); the `cache_settings` record here rebuilds the cache instead.
- Mask files: `<image stem>-masklabel.png` next to the image, always `.png` (also for `.jpg`/`.webp` images); a conditioning image is `<image stem>-condlabel.png`. A missing mask silently becomes an all-white mask (the whole image). A wrongly named one is no mask: `-mask.png` is even collected as a training image, `-masklabel.jpg` is skipped but not used.
- `normalize_masked_area_loss` divides by the mean of the area each term covers. Masked prior preservation's term covers the unmasked area, which is empty for an all-white mask (every image without a mask file), and 0/0 stopped the run with "Training loss became NaN" (upstream has the same code); the main term did the same with `unmasked_weight: 0` and an all-black mask. `masked_loss._area_mean` floors the mean at the smallest normal float, so such a term is 0 and every result that was finite before is bit-identical (300 random masks; tiny Chroma A/B). `GenericTrainer.start` prints, per concept, how many images have no mask (`concept_stats.images_without_mask`, collected like mgds `CollectPaths`).
- `masked_prior_preservation_weight` only takes effect for `TrainingMethod.LORA` (`GenericTrainer.py:744`); the UI shows it only then, and `unmasked_probability` only for `has_mask_input()` models.
- `custom_conditioning_image` only matters for models with a conditioning image input; `TrainConfig.uses_custom_conditioning_image()` gates the data loader and the cache record (elsewhere the extra image was still loaded and augmented, which changed the random augmentations).
- Models whose UI hides the text-encoder train switch (Anima, Krea2, Z-Image, Ideogram, Ernie, Flux2) still carry `text_encoder.train=True` from the defaults. Anima and Krea 2 now always cache text and predict from the cached hidden state, whatever the flag says (Anima crashed with `t5_ids` unbound; Krea 2 re-encoded every step).
- Loss weight functions depend on the loss: `ModelType.supported_loss_weights()` (flow matching: CONSTANT, SIGMA; diffusion: CONSTANT, P2, MIN_SNR_GAMMA, DEBIASED_ESTIMATION; Sana is flow matching but uses the diffusion loss, so CONSTANT only). The UI lists only those and `GenericTrainer.start` refuses others before loading (e.g. MIN_SNR_GAMMA on Chroma raised `NotImplementedError` after caching).
- mgds `DiskCache` keys the cache only by the concept (path, seed, subdirectories flag, image/text settings), not by model, resolution, dtypes or masking. With `clear_cache_before_training` off, those changes used to reuse stale latents silently (e.g. 128 px latents for a 256 px run). `GenericTrainer.start` now keeps `cache_settings.json` in `cache_dir` (`util/cache_util.py`) and rebuilds the cache when a recorded setting changed or the record is missing. A concept without a `seed` gets a random one per run, so its cache is never reused anyway.
- mgds `AspectBucketing` rounds each bucket side to the data loader's `aspect_bucketing_quantization` (64 for most models; SD 8, PixArt 16, Sana 32, Wuerstchen 128). Its narrowest bucket (1:4) has a short side of half the resolution, which rounds to 0 at a resolution of at most the quantization (and a `WxH` side of at most half of it), and mgds then divided by zero when the epoch started. `DataLoaderText2ImageMixin._check_bucket_resolutions` now raises with the smallest valid value (quantization + 1 for an automatic resolution) for the resolution and every enabled concept's resolution override.
- `dataloader_threads > 1` together with a text-encoder `offload_fraction > 0` raises an error.
- `GenericTrainer.start` refuses an enabled concept whose path is empty or not a folder, naming the concept, before the model loads (`__check_concept_paths`); mgds `CollectPaths` lists the folder only when the first epoch starts, and an empty path failed there as `FileNotFoundError: [Errno 2] No such file or directory: ''` (the user's `diag_ab` with a config whose concept had no folder; `diag_ab`'s own preflight only checks that the concepts file exists).
- Aspect batch sorting never mixes buckets and skips each bucket's leftover samples, so a small dataset can give an epoch with no batches. `GenericTrainer.train` then raises instead of counting through empty epochs (which would end without saving).
- Caching runs the encoders (VAE, text encoders) in `dataloader_threads` concurrent threads (mgds `PipelineState` executor), so with the default 2, two samples are prepared at once. A `CheckFinite` module (`dataLoader/pipelineModules/`) in front of each disk cache stops caching with the file name when an encoding has NaN/inf. Seen on ROCm (gfx1100, torch 2.13+rocm7.2): a random image's latent came out all NaN, and the same image encoded fine on a rerun. The cause turned out to be the AOTriton head-size-512 bug in the VAE's attention (see Attention), not concurrency; the shared lock the model-holding pipeline modules take (`DataLoaderMgdsMixin._run_models_one_at_a_time`) stays, so encodes run one at a time while loading/cropping stays parallel, and the cache is bit-identical to `dataloader_threads: 1`. The lock wrapper pre-fetches each module's `get_inputs()` and must skip `None` entries: mgds lists unused optional inputs as `None` (`EncodeT5Text` without an attention mask), and fetching them crashed every Flux.1, SD3/3.5 and HiDream run at caching (`'NoneType' object has no attribute 'split'`).
- The NaN-loss check runs **before** `optimizer.step()` (`GenericTrainer.train`), so a NaN batch never reaches the weights or optimizer state; with a fused back pass the update already happened during backward. It also stops on an infinite loss (which broke the weights the same way), except with an enabled fp16 grad scaler, which skips such steps itself. `CustomGradScaler` is built for device `cuda`, so it is disabled (but not `None`) on a CPU run.
- Validation (`GenericTrainer.__validate`) runs like sampling: model in eval mode (no LoRA/T5 dropout), schedule-free optimizers switched to their averaged weights (`__before_eval`), then `setup_train_device` and `optimizer.train()` restore training. It measures the raw weights, not EMA.
- Default samples are queued and run only when no gradient is pending (`__execute_sample_during_training`), so with gradient accumulation a sample waits for the next update. `default_sample_queued` keeps one in the queue: a "sample now" request (`get_and_reset_sample_default_command`) on a scheduled step or while one waits is used up silently. Before, the request stayed set behind the scheduled sample's `or` and sampled again on the next step, and with accumulation 2 and `sample_after` 1 STEP every update sampled twice (tiny Chroma: steps [0, 2, 2, 4, 4, 6, 6], now [0, 2, 4, 6]).
- Noise options ported from the adv_optm author's fork, all off by default: CIOP (`ciop_noise_weight`, `ciop_p`: noise on the noisy input and the loss target), CEP (`cep_gamma`: uniform noise ±γ/√d on text encoder outputs) and Immiscible Diffusion (`k_noise_sampling` > 1: nearest of k noise candidates per sample, distances in fp32 since fp16 overflows and has no CPU `cdist`). CIOP/CEP are hooked into every `Base*Setup.predict` and skipped when `deterministic` (validation); the immiscible pick is in `_create_noise`, so validation uses it too (deterministically). A new model setup has to call `_apply_ciop`/`_apply_conditional_embedding_perturbation` itself.
- The sampled timestep indexes the noise schedule (`num_train_timesteps` entries). The continuous distributions could reach `num_train_timesteps` itself: LOGIT_NORMAL's sigmoid rounds to exactly 1 above ~16.6, so with the Chroma presets' noising weight 7.7 (kept when only the distribution is switched) 2.35% of the samples were 1000. On the CPU that is an IndexError; on the GPU a device-side assert, which **aborts the process under ROCm** (exit code -6, no traceback: the GPU check's noise-options run died of it, its CPU run passed by luck). HEAVY_TAIL (`1-u-s·(cos²(πu/2)-1+u)`) leaves 0..1 on both sides for noising weights below -1 or above 7.235 (24% of the samples at 7.7; negative ones indexed the schedule from its end), BETA reaches 1 for small u. `_get_timestep_discrete` clamps into the schedule; every sample that was inside it is unchanged (old vs new over 60 settings, a 2-epoch run bit-identical). The discrete distributions refuse weights that are all 0 or NaN (`_valid_timestep_weights`: INVERTED_PARABOLA with its peak far outside 0..1, shift 0), which `torch.multinomial` checks only inside the GPU kernel for batches above 1. The timestep preview plots `range=(0, 999)`, so it never showed the samples at 1000; they are at 999 now. On the 7900 XTX (0953151) the timestep check (164 settings) and every training feature pass, the noise-options run included.

**Layer / activation offloading** (`modules/util/LayerOffloadConductor.py`)
- Async transfers use three streams (train = default, layer, activations) and are on whenever `train_device` is `cuda` (ROCm too) and `async_offloading` is on. Temp-side caches are pinned with `cudaHostRegister`/`hipHostRegister` only in async mode; `async_offloading: false` = synchronous copies, no pinned memory.
- Each offloaded block is a `BoundaryOffloadCheckpointLayer` (preview-2 #1649): a non-reentrant checkpoint, with the conductor driven by the `LoadBoundary`/`EvictBoundary` autograd Functions outside the block, so a compiled block stays one graph. Without grad (sampling, frozen parts) it calls the conductor inline.
- Stream-ordering invariants (fixed bugs, keep them): a layer offloaded during the **back pass** waits for all train work queued so far. The boundary path already records its event after the layer's backward kernels (which read the weights; fused back pass also updates them); the wait stays as a guard. Pinned buffers must only be unpinned after a device sync (`unpin_tensors_`), and are pinned only with async transfers (the simplex `FullModelLayerAllocator` too).
- Offloadable parts: every transformer, T5/LLM/CLIP text encoder, the SD/SDXL UNet (its transformer blocks, in down→mid→up order; `model.modules()` lists up before mid), and the Wuerstchen/Stable Cascade prior (a Cascade UNet with repeating blocks is rejected). Not: VAE, effnet, decoder. Conductors live in the `model.offload_conductor` dict, keyed by the part's attribute (SD/SDXL/Wuerstchen by the part's stem), where `BaseModel._move_part` finds them. A layer list must be in exact execution order, one call per layer per step.
- When a part offloads, diffusers' own `gradient_checkpointing` must be off on the modules whose blocks OneTrainer wraps (Transformer2DModel, the priors): a nested checkpoint re-runs the offload forward in the middle of the back pass. Without offloading it is left as it was.
- `_kwargs_to_args` turns kwargs into positional args (the boundaries wrap positional tensors only); arguments only a `**kwargs` parameter takes are passed by name to the block and its recompute (CLIP's `is_causal=True`; OneTrainer calls CLIP without a mask, so dropping it meant non-causal attention, which upstream's version still does). A grad-requiring tensor passed by keyword raises.
- LLM text encoders must be called with `use_cache=False` when grad can flow through them: a checkpoint recompute appends to the KV cache again. Qwen/Z-Image/Anima/Krea2/Ideogram don't pass it, which is fine only because their encoder never runs with grad.
- Activation offloading moves autograd's saved copies of the declared block inputs (`saved_tensors_hooks`, matched by view, not identity), so the inputs themselves stay untouched.
- Offloading a trained part needs `gradient_checkpointing` (`enable_checkpointing` raises otherwise); frozen parts offload without it. Only `nn.Linear`/`Conv2d` weights+bias (and SVD/NF4 parts) are offloaded (`quantization_util.get_offload_tensors`).
- Test offloading on CPU by driving the real conductor with `train_device="cpu"`, `temp_device="cpu:1"` (different to `device_equals`, same memory).
- `stream_from_disk` (default **true** since preview-2, `modules/util/disk_stream.py`) loads a part as a meta skeleton and streams its weights from the checkpoint straight to the train device (quantized there) the first time it is used, so the unquantized part never sits in RAM. On eviction `cache_in_ram` (default true; `model.cache_in_ram` is keyed by part name, the other per-part dicts by stem, so a lookup by stem made `text_encoder_1` ignore it) keeps the weights on the temp device; without it they go back to meta and are re-streamed, which a fully fine-tuned part can't do (raises). `TrainConfig.streams_from_disk()` is false when the train and temp devices are both CPU (a streamed part stayed a meta skeleton there). `simplex_offloading` (needs layer offloading and streaming, frozen parts only) keeps a part in one flat RAM buffer. The SDXL setup skips `quantize_layers` for streamed parts (it quantized the meta skeletons). `rocm_check --only streaming` streams a toy part through the loaders' own closure (`HFModelLoaderMixin.__finish_sub_module_load`) and compares it with the RAM-loaded one (`__convert_sub_module_to_dtype` + `quantize_layers`): bit-identical weights in bf16 and fp8, whole and per layer under offloading/simplex, cache in RAM on and off; it needs a GPU (on the CPU only a dry run with the device-type comparison patched).
- GPU memory for offloading and part moves sits in dedicated `torch.cuda.MemPool`s (`torch_util.create_mem_pool`) on NVIDIA. On ROCm they're off unless `OT_ROCM_MEM_POOLS=true`: they're another allocator mode, and `expandable_segments` (the other one) gives wrong results on the 7900 XTX. `rocm_check --only mem_pool` A/B-tests them (offloading, streaming, part moves). On the 7900 XTX (42a68fe) they gave correct results. `diag_ab` on the user's Chroma LoRA config (d311fb3, 2 runs each): bit-identical losses and weights, and no gain. Without layer offloading the pools hold only the LoRA (0.35 GiB; streamed weights go to the default allocator); with `transformer.offload_fraction=0.5` they hold the 8.9 GiB of resident layers, but peak reserved (13.9 GiB), fragmentation and step time are unchanged, with ~8-13% more hipMalloc/hipFree and part moves ~2% slower. So they stay off on ROCm. The same runs give offloading 0.5 vs none: peak reserved 13.9 vs 21.9 GiB, 8.45 vs 7.83 s per step.
- `materialize()` copies each layer's offloadable tensors straight into the static cache of the device the layer starts on and moves only the rest of the layer to the train device (`__layer_to_device`); it used to move every layer whole to the train device first (offloaded ones there and back).

**GPU memory**
- `BaseModel.materialize/evict/materialize_only` is the only way parts reach the train device, and `materialize_only` evicts before it loads, so two large parts (e.g. Chroma's 17.8 GB bf16 transformer and 9.5 GB T5) are never resident together. Sampling, caching and backups only swap between optimizer steps, after `zero_grad(set_to_none=True)`.
- PyTorch 2.13's caching allocator logs `memory allocation failed with OOM on device 0 while trying to allocate N bytes` (`HIPCachingAllocator.cpp:3934`, `LOG(WARNING)` in `alloc_block`, new in 2.13) at every failed hipMalloc, the first attempt included; `malloc` then frees unused cached blocks (`release_available_cached_blocks`, then `release_cached_blocks`) and retries, and MIOpen's workspace allocation (`Conv_miopen.cpp`) catches a remaining OOM and falls back to the default algorithm. The user saw it during caching (5.1 GiB requested, 0.4 GiB free) while caching went on: harmless, documented in docs/RunDiagnostics.md ("Terminal messages that look like errors"). Silencing it would need `TORCH_CPP_LOG_LEVEL=ERROR`, which hides every C++ warning, so it is left alone.
- `OT_LOG_VRAM=true` prints tensor/reserved/free GPU memory after every load and unload; an OOM while loading a part prints which part and the same numbers (`torch_util.vram_summary`). Debug mode or `OT_DEBUG_PROFILES=1` also prints allocator fragmentation after part moves (`print_fragmentation`); `OT_DEBUG_PROFILES=1` on a CPU run crashes in the CUDA memory profiler.

**EMA / saving**
- Intermediate saves and the final model contain **EMA weights** when EMA is on (`GenericTrainer.__save`, `end`). Backups keep raw weights plus EMA state. `EMAModuleWrapper.copy_ema_to(store_temp=True)` keeps a copy of the raw weights (`.to("cpu", copy=True)`). With `.cpu()`, weights already on the CPU shared their memory with that copy, so the EMA weights stayed in place of the trained ones. That hit every intermediate save, GPU runs included, because `train()` evicts the model (LoRA too) to `temp_device` before `__save`; on a CPU run it also hit EMA sampling.
- Schedule-free optimizers switch to eval **before** the EMA weights are copied in, in `__save` as in `end()` and sampling (`__save` used to copy first, so intermediate saves held eval(EMA), up to 5.6e-3 off the final save of the same state), and back to train in its `finally`: a failed save used to leave the optimizer in eval mode, and schedulefree's next `step()` raised.
- EMA updates run only every `ema_update_step_interval` (default 5) optimizer steps but use the per-step decay, so the effective horizon is about `interval/(1-decay)` steps (≈5000 at defaults). Decay ramps as `(1+s)/(10+s)`. With EMA on, `non_ema_sampling=true` (default) doubles the sampling cost.
- `ema_stochastic_rounding` (default on) rounds the EMA update stochastically when the EMA weights are bf16 (bf16-trained weights); float32 EMA weights are unaffected (bit-identical runs). Without it an update at decay 0.999 is mostly below bf16 precision and lost (a weight moved by 8 ulps left the EMA unchanged over 1000 steps). EMA weights from a backup keep their saved dtype, so the update works on an explicit fp32 copy (`.to(..., copy=True)`); `.to()` alone returned an fp32 parameter itself and the in-place update changed the trained weights.
- **Continue from Backup** (`continue_backup_path`, general tab, default empty; the user's feature 2026-11-06): resumes one chosen backup folder (weights, optimizer state, progress: e.g. epoch 10 of a run that went on to overtrain) and wins over `continue_last_backup`, which stays for crash recovery. `TrainConfig.get_resume_backup_path` is the one place that picks the backup (GenericTrainer, the sample window); `check_selected_backup` (also at the top of `GenericTrainer.start`, before caching) stops on a path that isn't a folder, has no `meta.json`, or was made with another model type, method or adapter, where the last-backup search skips such folders. In the UI the two exclude each other (user decision): a non-empty field greys out the last-backup switch, the switch on greys out an empty field (a config with both set keeps the field usable and the switch greyed, matching what training does). The field stays set after a run (user decision: trust the user; an earlier version emptied it). The field has the normal entry width. The folder picker opens in `<workspace>/backup` (`path_entry(initial_dir=...)`, both toolkits), and the field flags a folder without `meta.json`. Cloud runs upload a selected local backup (`CloudTrainer` maps it like `lora_model_name`; `cloud:<path>` names one already there). Tiny Chroma on the CPU (3 epochs, a backup per epoch): continuing from the epoch-1 backup with Continue from last backup also on ended bit-identical to the uninterrupted run; a missing folder, one without `meta.json` and a LoHa backup in a LoRA run stopped before the model loaded.
- Ctrl-C in `scripts/train.py` saves only if `backup_before_save` is true, and `end()` saves nothing unless at least one optimizer step ran. On an exception, `end()` is skipped (no save) and only TensorBoard is stopped.
- `update.sh`/`install.sh` run `pip --upgrade-strategy eager -r requirements-rocm.txt`, which **reinstalls the pinned torch** (`2.13.0+rocm7.2` today) over any manually installed build.

**torch.compile (Compile transformer blocks, `config.compile`, default off)**
- Only the denoiser's repeated blocks are compiled (`checkpointing_util.enable_checkpointing` with `config.compile`): never the text encoders, the VAE or the Wuerstchen/Stable Cascade prior; on SD/SDXL only while the UNet's checkpointing or offloading is on. Without offloading each block becomes a `CheckpointLayer` compiled with `fullgraph=True` (the checkpoint traced inside, so the min-cut partitioner trims the recompute); with offloading `BoundaryOffloadCheckpointLayer` compiles only the checkpointed block and the conductor runs in `LoadBoundary`/`EvictBoundary` outside the graph. Compiling is lazy: the first forward (often the first sample) pays for it, and the progress bar shows "compiling kernel N forward (variant #k)".
- Every block of every model shares one code object (`CheckpointLayer.forward`, or `__checkpointed_block`), so guards pick the variant: tiny Chroma LoRA compiles 8 (sampling double/single; training first double block (input without grad), other double blocks, single blocks, each with and without the text attention mask), never one per block. The double and single blocks' different sequence lengths make dynamo mark sequence dims dynamic at the second compile (automatic dynamic, saved as PGO in the cache), so resolution and caption length changes don't recompile. A later run in the same process reuses the variants (UI: 8, 0, 0 compiles over three runs). `init_compile` raises `recompile_limit` and `accumulated_recompile_limit` (8 and 256 by default, fullgraph raises at either) to 8192, also as the config entries' defaults, because dynamo's config is per thread since torch 2.12 and the GPU's autograd worker thread (diffusers' own checkpointing on SD/SDXL runs compiled blocks there) never calls it.
- CPU, tiny Chroma 3+3 blocks, 32 steps (torch 2.13): no graph breaks with LoRA, DoRA, LoKr + DoRA, OFT (with CANS since the op above), float8, offloading, no checkpointing; SD UNet gradients match eager to 2e-6 (fp32). Cold run 107 s vs 25 s eager, warm 24 s; a new variant mid-run (a batch without the mask) stalls one step. On the 7900 XTX (ad3458e): the bare block 1.04x, the block as training compiles it (LoRA on every layer, checkpointing) 1.28x (7.58 vs 5.91 ms) but peak allocated 401 vs 341 MiB; GEMMs stay rocBLAS (TunableOp still applies) and attention AOTriton, inductor's Triton kernels fuse the elementwise glue. **Attention**
- `attention_mechanism`: `SDP` = diffusers "native" (torch SDPA picks its own kernel); `FLASH` = diffusers "flash" (the flash-attn package, **CUDA-oriented**); `CUDNN` = **CUDA-only** (not built into ROCm PyTorch; `GenericTrainer.start` stops on it under ROCm); `FLEX` = torch FlexAttention. Chroma always passes a text attention mask when captions are padded (`BaseChromaSetup.predict`); `ChromaModel.encode_text` cuts the text to the batch's longest unmasked length, rounded up to a multiple of 16 when a mask is needed.
- Measured on the 7900 XTX (`rocm_check --full`): SDPA picks FLASH without a mask and EFFICIENT with bool or same-dtype masks (fp32 → EFFICIENT always); a float32 mask with bf16 q/k/v → MATH (up to 30x the memory). All backends match the fp64 reference, including fully masked rows. bf16 linears reach 80-100 TFLOPS; TunableOp made two of three GEMM shapes 1.2-1.3x faster, `MIOPEN_FIND_MODE=FAST` changed nothing. PyTorch's default BLAS library on gfx1100 is already rocBLAS (`preferred_blas_library()` = Cublas), so `TORCH_BLAS_PREFER_HIPBLASLT=0` was a no-op (bit-identical training runs), and `=1` is ignored there too (fa85fea: the child still reported Cublas, and a `diag_ab` run with it was bit-identical to the baseline, 7.79 vs 7.81 s per step), so hipBLASLt can't be chosen this way on gfx1100; the runtime-switch check now tests the library that isn't the default and prints the one each child used, and compares each switch's linear forward/backward with fp64 (TunableOp's tuned GEMMs: 1.69e-3, the same as the default's). Its TunableOp run reuses the `rocm_check_tunableop*.csv` an earlier run left in the output folder and says so (it was labelled "tuned in this run" either way: 40 s fresh vs 2 s reused at 9ff4f54). Its default child's times vary between runs (0.68 vs 1.17 ms for the same 4096x640x5120 kernel), so only ratios within one run compare; the in-process per-family benchmarks are steadier. `diag_ab` on the user's Chroma LoRA config (cd47146, `PYTORCH_TUNABLEOP_ENABLED=1`): 7.09 vs 7.83 s per step (-9%), tuning once took ~10 min (first run 1036 vs 419 s; caching 57 vs 22 s, the T5/VAE GEMMs get tuned too) and the second run reused `tunableop_results0.csv` (then in the repo root, now `diagnostics/tunableop/`); peak reserved +0.5 GiB (least free 1.0 vs 1.5 GiB); losses differ from step 0 on (max rel 1.6e-2) and LoRA weights up to 1.5 apart, repeats bit-identical, so the GEMMs round differently. Against a seed change (90dc2df, `OT_SEED=43`: a different LoRA start, same data and noise, since step 0 matched): TunableOp's step-0 loss differs by 1.1e-3 (one forward with the same weights: bf16 rounding), mean loss 0.23044 vs 0.2304 (seed 43: 0.23038), median saved-tensor difference 3.3e-2 vs 0.64 for the seed; the largest (~1.5) is a LoRA B tensor in both. So TunableOp changes the result far less than two ordinary unseeded runs differ; int W8A8 fwd+bwd ran at 0.77x of bf16.
- **AOTriton bug on gfx11 above head size 256** (measured on the 7900 XTX): flash and memory-efficient SDPA at head size 512 give wrong outputs (rel err 1-17) and NaN gradients in fp32/bf16/fp16; the math kernel is right. PyTorch's `aotriton_max_hdim()` limits gfx11 to 256 only for AOTriton 0.11, and torch 2.13 ships 0.12b (AOTriton 0.14, in the ROCm 10.1 builds, has no gfx110x kernels above 256: the call fails instead). Every VAE's mid-block attention is one 512-wide head, so VAE encodes/decodes (cached latents, sample images) were off (the real Flux/Chroma `ae.safetensors` latent by 9%, a random-init VAE's by 25-40%), and nondeterministically so (that was the "random all-NaN latent" too, not thread concurrency). `modules/util/rocm_sdpa_fix.py` wraps `F.scaled_dot_product_attention` (installed by `script_imports()`) and sends head sizes > 256 on ROCm gfx11 to the math kernel, chunked along the query length (~512 MiB score blocks). It calls `torch.ops.aten._scaled_dot_product_attention_math` directly (bool masks converted to -inf as SDPA does; bit-identical to SDPA's math backend). Never use `torch.nn.attention.sdpa_kernel` in code that can run in threads: it sets process-global flags and restores what it saw on entry, so two overlapping threads leave flash/efficient attention off for the whole process (the first version of the fix did this during caching's worker-thread encodes, and every later attention ran the math kernel: 5x slower, +2 GiB at SD1.5 512 px, OOM at 1024 px; confirmed fixed on the 7900 XTX: after the concurrent-encode check, default attention runs at flash speed again, 3.0 ms at SD1.5 512 px). `rocm_check` fails any check that leaves these flags, `cudnn.enabled` or the fix's install state changed. `cache_settings` records `vae_attention`, so caches made without the fix rebuild once on such GPUs (None elsewhere, as in older records). `rocm_check` tests PyTorch's raw kernels through `original_scaled_dot_product_attention` (a WARN there is this bug) and OneTrainer's path separately. Confirmed on the 7900 XTX with the random-init and the real Flux/Chroma VAE: with the fix every encode (main thread, worker threads, concurrent) matches the CPU (rel err 3e-6 / 1.8e-5); without it the latent is 0.38 / 0.087 off, first wrong layer `mid_block.attentions.0.to_out.0`.
- ROCm SDPA (torch 2.13 = AOTriton 0.12b): flash and memory-efficient attention are on by default for gfx1100/gfx942/gfx950/gfx1151/gfx1201; gfx1101-1103, gfx1150/1152/1153 and gfx1200 are "experimental" and need `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`, else SDPA silently uses the math kernel. On ROCm only, a float mask whose dtype differs from q/k/v also drops to math (a warning, then slow and memory-hungry); today every model passes a bool mask or one in the train dtype.

**Security: cloud training** (2026-11 audit; tested end to end only against a local fake SSH server, attached and detached, not a real RunPod pod or SSH host)
- The PC and the cloud trainer exchange JSON lines (`modules/cloud/cloud_messages.py`): callbacks from `train_remote.write_request` to `LinuxCloud.exec_callback`, commands from `LinuxCloud.send_commands` (`TrainCommands.to_dict`) to `train_remote.command_thread_function`. Both directions were pickled, so the cloud machine, anyone on the path or an install command could run code on the PC. Only the six callbacks in `_CALLBACKS` exist, their arguments are type-checked, a sample is a base64 JPEG opened with `formats=["JPEG"]`, a callback file over 64 MiB is dropped, and bad lines are skipped with one message. A command flag counts only if it is `True`; custom samples must be dicts and go through `SampleConfig`.
- SSH host keys (`modules/cloud/ssh_host_keys.py`, `HostKeys`): fabric's default accepted any key and never read `known_hosts`. A Linux cloud (`TRUST_FIRST_HOST_KEY = False`) needs the host in `~/.ssh/known_hosts`; the error names the fingerprint and the `ssh -p` command that adds it. A RunPod pod (`True`) is new every time, so the first key seen after authentication is pinned for the run, and every later connection, scp included (`StrictHostKeyChecking=yes` with a temporary `UserKnownHostsFile`), must match it.
- `BaseSSHFileSync.sync_down_dir` skips remote entries outside the remote folder or with `..` (`Path.relative_to` keeps `..`, so a listing could write anywhere on the PC). sshpass reads the password from `SSHPASS` (`-e`), not its arguments.
- The Hugging Face token reaches the remote shell as a file (`(umask 077 && cat > <remote_dir>/<run>.token)` over stdin), which the run command reads into `HF_TOKEN` and deletes; it used to be in the command line (visible in `ps`, and invoke's `UnexpectedExit` prints the whole command). Remote paths are `shlex.quote`d, `~/` becomes `"$HOME"/`.
- A cloud run asks first: a dialog in the UI, `Start it? [y/N]` from `train.py` on a terminal (no prompt without one), showing `CloudConfig.describe_run` (machine, install command with a note if it isn't the default, end and detached actions, workspace deletion).
- RunPod: the pod image is pinned by digest (`RunpodCloud._IMAGE`), `ports="22/tcp"`, no third-party template. The remote checks out this PC's commit (`git_util.get_git_commit`, `LinuxCloud.__checkout_local_commit`: fetch by SHA, detached); a commit the remote can't fetch (not pushed) falls back to the default branch with a warning. `update.sh` then runs with `OT_UPDATE_SKIP_GIT_PULL=true`.

## Working rules for Claude
